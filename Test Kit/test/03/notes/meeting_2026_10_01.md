passwords in the failing tests. `Sup3r_secure` vs `sup3r_secure`, the

runtime is matching against the struck section. The data path is the
bug; the inline migration carried junk across.

Priya: signup-side we just display the rule list the library returns.
If the library says "too common" we show "too common". The tickets are
consistent with what the library emits.

t.oka: has anyone actually READ the rule ids in the failing tests? The
log in build #292 prints them: min_length and needs_special. Not
blacklisted. If the runtime were matching the struck section, the id
would be blacklisted. The 8-char password fails a LENGTH check. The
underscore password fails a SPECIAL check. Those are policy rules, not
the list.

r.alvarez: the ids could be misleading if validate() short-circuits or
if the mapping from id to check got scrambled in the same release. The
release touched the blacklist path AND the rule plumbing. I am not
ready to exonerate the data layer on the strength of a label.

Priya: cost check. The data-path patch is an afternoon. Re-opening the
policy rule review is a week and pulls in the security council. We do
the cheap one first; if patch v2 stays red we escalate to a full read
of policy.py against docs/policy.md.

Consensus: proceed with r.alvarez's loader patch (v2, active-section
parser). t.oka to verify the rule-id emission path as a side quest,
timeboxed to one day. Revisit only if both come back empty.
